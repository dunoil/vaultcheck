Self serve, about 10 minutes

Try VaultCheck in about 10 minutes

Run the full VaultCheck pattern under your own Terminal 3 identity, with your own free developer key. No prior knowledge of VaultCheck is assumed. Back to the eligibility desk or the traction dashboard.

What you will prove

By the end of this guide you will have, on Terminal 3 testnet and under your own DID:

  1. Registered your own copy of the VaultCheck vault contract, with a private data map that only the contract can read or write.
  2. Stored a fictional sample record inside that vault. The raw record never leaves the enclave.
  3. Created an agent and granted it exactly one function, check, for 90 days.
  4. Watched the agent answer six eligibility rules with one boolean per rule, and no underlying values.
  5. Watched the node reject the agent when it tries a function it was not granted (HTTP 403).

One script, try.ts, does all of it. You only bring your own key.

Prerequisites

  1. A free Terminal 3 developer key. Go to terminal3.io/claim-page, sign in with Google, and claim a key. The key is shown once and comes with free testnet credits. Copy it somewhere safe for the next step. Never share it, never commit it to git, never paste it into an issue or a chat.
  2. Node 20 or newer and git installed. That is all: no Rust toolchain is needed, because the script downloads the prebuilt vault contract from the VaultCheck GitHub release automatically.
  3. Optional, only for rebuilding the contract yourself: a Rust toolchain with the wasm32-wasip2 target (via rustup, then rustup target add wasm32-wasip2). A local build is used in preference to the download when one exists.

The steps

Step 1. Clone the repository and install dependencies.

git clone https://github.com/dunoil/vaultcheck.git
cd vaultcheck
npm install

Step 2. Put your key in a local environment file. Create a file named .env in the repository root with one line. The file is for your machine only.

T3N_API_KEY=your key from the claim page

Step 3. Run the onboarding script.

set -a; . ./.env; set +a
npx tsx try.ts

There is no build step. On the first run the script downloads the prebuilt vault contract (220,578 bytes) from the VaultCheck GitHub release v0.1.0, checks its WASM header, and saves it locally for later runs. If you already built the contract yourself, your local build is used instead.

The script prints numbered steps as it goes: authenticate, register the contract, create the private map, store the sample record, create an organisation and an agent, grant check only, run the check, and attempt the ungranted call. It funds the agent from your testnet balance (5 credits at creation, plus a 10 credit top up only if the check needs it).

What success looks like

The run ends with a summary and a share back line like this one (your DID and contract will differ):

VaultCheck onboarding complete | DID: did:t3n:your-did-here | Contract: z:your-did-here:vault | contract_id: 1234

The check result above it shows six booleans, all true for the sample record, and the ungranted call shows a rejection with HTTP 403. If you see both, the pattern worked end to end under your identity.

Report your DID and be counted

Your run only counts as a verified external user on the traction dashboard after you report it:

  1. Open a new issue at github.com/dunoil/vaultcheck/issues.
  2. Paste your share back line (DID plus contract) as the issue text. Nothing else is needed, and never include your API key.
  3. We verify the DID and contract against the network record, then add your run to the public activity log as an external onboarding completion.

This verification step is deliberate. The dashboard separates internal DIDs (the project itself) from external DIDs (independent users), and external entries are added only from verified reports, never estimated.

Troubleshooting

SymptomWhat it means and what to do
The granted check returns 403 Per the official Terminal 3 walkthrough, a bare 403 on a granted call can also mean the agent is out of credit. try.ts already tops the agent up with 10 credits and retries once. If it still fails, claim or wait for more testnet credits and run again.
Contract registration says the version is not higher than the current version Your DID already registered this contract in an earlier run. try.ts detects this and continues with your existing contract. Nothing is wrong.
The WASM download fails, or the WASM file is not found The script downloads the prebuilt contract from the GitHub release automatically and says so in Step 2 of its output. If the download fails (for example offline), the script prints the fallback: build it yourself with rustup target add wasm32-wasip2 and cargo build --release --target wasm32-wasip2 inside contract/, or download the asset manually and set T3N_WASM_PATH to its location.
T3N_API_KEY is not set The environment file was not loaded. Re-run the set -a; . ./.env; set +a line in the same terminal, then run the script again.
Key safety Your key controls your testnet identity and credits. Keep it only in your local environment. If you ever paste it somewhere public by accident, treat it as compromised and claim a fresh setup.
